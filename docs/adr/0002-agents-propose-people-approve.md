# ADR-0002: Agents may propose to the memory graph; people approve, and the text stays verbatim

**Status:** Proposed. A working prototype is on `feat/neo4j-memory-graph`.
**Date:** 2026-09-29
**Deciders:** Emori hack-day team (Bryson, funkstop)
**Builds on:** [ADR-0001](0001-neo4j-memory-graph.md)

## Context

Growing the graph by hand does not scale, and models are good at exactly the fuzzy work involved: noticing which passages in something Leo wrote are worth keeping, and pulling out the people, places and feelings in them. But ADR-0001 fixed invariants that an agent must not break:

- A memory is Leo's own words, stored verbatim, with his consent.
- AI-generated text never becomes a memory.
- Nothing is invented: no memory, date, relationship or event the text does not contain.

The runtime report adds two constraints: put an approval step in front of anything that writes, and do not assume tool calling works on Crusoe.

## Decision

Agents may **read and propose**. They never write. A person approves every change.

Two agents ship in the prototype. Each is a single chat completion through one shared function (`askModel`), so neither needs tool calling or a structured-output mode and both work on OpenRouter and Crusoe.

**1. Memory scout** (`POST /api/memory/propose`). Given something Leo wrote, it proposes passages worth keeping.

- It only ever sees the user's own words. The server drops every non-`user` message before calling the model.
- Each proposal must quote the source **verbatim**. The quote is located in the source text (tolerating only whitespace and wrapping quotation marks) and replaced with the exact source substring. Paraphrases, merged passages and quotes that are not in the text are dropped.
- Its claims about a passage are validated like any model output: entity names must appear in the quote, relations must join two kept entities, and a date needs a year the quote states.
- Passages already saved are flagged and cannot be selected again.
- The route is read-only. It saves nothing.

**2. Ask the graph** (`POST /api/memory/ask`). Answers a question using only the saved memories.

- While the graph is small the model sees every memory, oldest first. Beyond 12 it sees recalled memories instead.
- It must cite numbered memories. Citations are normalised, and any that point outside the context are removed.
- The answer is **AI-generated**. It is returned and shown labelled "Generated by AI · not saved", and it is never stored. This is the same rule the "How Emori remembers" dialog already states for Mateo's replies.
- Cited memories light up on the graph, with the entities that connect them.

**What approval means.** Saving goes through the existing `POST /api/memory/entries`. The user ticks the passages to keep and saves them. The server honours a proposal's connections only when the request says `via: "scout"`, re-validates them against the text, and labels them `scout`. Anything else runs the server's own extraction.

**Untrusted text.** Memory text and pasted writing are data. Wrapper tags are stripped before prompting, and the prompts say the content is data, not instructions. Model failures surface as a typed `ModelError` and a 502, and the tools are disabled with an explanation when no model is configured. Nothing else depends on them.

**Deterministic tools stay model-free.** Tracing the shortest connection between two nodes, and listing the threads shared by Leo's memories and Mateo's stories, are computed from the graph alone.

## Options considered

### Option A: Let an agent save what it thinks matters

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | One model call per message |
| Scalability | Good |
| Team familiarity | High |

**Pros:** effortless; the graph grows on its own. **Cons:** breaks consent and the verbatim rule. A model would decide what Leo "said", and mistakes become permanent memories. Rejected.

### Option B: A tool-calling agent with a write tool behind an approval step

| Dimension | Assessment |
|---|---|
| Complexity | High |
| Cost | Several model calls per task |
| Scalability | Good |
| Team familiarity | Medium |

**Pros:** more flexible; the agent can explore the graph and decide what to look up. **Cons:** tool calling is unverified on Crusoe, and there are more moving parts to secure and test. Deferred, not rejected. It can be layered on later, since the write path and its approval rule do not change.

### Option C: Single-shot agents that propose, with people approving (chosen)

| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Cost | One call per action the user takes |
| Scalability | Good |
| Team familiarity | Medium |

**Pros:** every guarantee is enforced in code and tested. It works on both providers. Answers are explainable through citations and highlights. **Cons:** one extra click per batch, and quality depends on the model returning the requested JSON.

### Option D: No agents

**Pros:** nothing new to trust. **Cons:** the graph only grows by typing, and there is no way to ask questions of it.

## Trade-off analysis

The graph is only worth having if Leo trusts that it contains his words and nothing else. Option A trades that trust for convenience. Options C and B keep it. C gets most of the convenience with much less machinery, and it does not depend on a capability we have not verified. The approval click is the price, and it is also the consent step the product already promises.

## Consequences

**Easier**

- Turning a journal entry or message into several connected memories in one pass, with consent.
- Explaining an answer: every claim points at a memory, and the memories are highlighted.
- Testing: the guarantees live in pure functions and route handlers, and run against a mock model.

**Harder**

- The scout is paste-based. It does not yet watch the live conversation or offer to remember something as Leo says it.
- Recall for questions is lexical once the graph exceeds 12 memories, so a paraphrased question may miss relevant memories.
- Every propose or ask call sends memory text to the model provider. Chat already does this, but it is worth stating.
- Each call costs money and the routes are unauthenticated, so they need rate limits before any public use.

Done in the prototype:

2. [x] Scout with verbatim-quote validation, duplicate detection, and user-only input.
3. [x] Ask with citation validation, and highlighting of the evidence.
4. [x] `via: "scout"` approval path with server-side re-validation.
5. [x] Trace-a-connection and shared-threads views, with no model.
6. [x] Unit tests, and integration tests that run the real handlers against Neo4j with a mock model.

Open:

1. [ ] **Evaluate with a real model.** Only a mock server has exercised the agents. Check that the model follows the JSON format, and measure how many proposals are dropped for not being verbatim.
2. [ ] Test adversarial memories and pasted text for prompt injection.
3. [ ] Add authentication and rate limits to `propose`, `ask` and `entries`.
4. [ ] Offer "Remember this?" from the live conversation, sending only the user's messages to the scout.
5. [ ] A curator that proposes merges and links between entities (for example "Dad" and "father"), approved the same way.
6. [ ] Embeddings, so recall survives paraphrase (see ADR-0001).
